# Boot architecture and generations

[Back to project home](../README.md)

This document uses `v0.1.0-alpha` / `c26c2c1` as its baseline. systemd-boot is the
approach currently in use and verified by the maintainer on hardware; the earlier
rEFInd + UKI implementation is preserved in the Git history.

## Boot chain

```text
Project Aloha UEFI
  └─ EFI/BOOT/BOOTAA64.EFI: systemd-boot
       ├─ NixOS: linux + initrd + devicetree + options
       │    └─ Linux EFI stub → initrd → init of the selected generation → system and desktop
       └─ Android: EFI/Android/Reboot2Android.efi
```

[`nixos/boot.nix`](../nixos/boot.nix) uses native NixOS configuration:

```nix
boot.loader.systemd-boot.enable = true;
boot.loader.systemd-boot.installDeviceTree = true;
hardware.deviceTree.enable = true;
hardware.deviceTree.name = "qcom/sm8150-xiaomi-nabu.dtb";
boot.loader.efi.efiSysMountPoint = "/boot/efi";
boot.loader.efi.canTouchEfiVariables = false;
```

The current deployment relies on the removable-media fallback path and does not
depend on BootOrder registration in the firmware NVRAM. The Android boot program and
GopRotate are deployed through `extraFiles`, and the Android menu is declared with
`extraEntries`; both groups of settings are also used for the initial ESP image
build. The menu rotation driver comes from the earlier nabu boot resources and does
not mean that rEFInd still boots the system. See the
[desktop notes](desktop.md#screen-orientation) for the landscape settings at
each stage.

## Why a UKI is not needed

The key is providing the kernel with a correct, matching DTB. systemd-boot loads the
external file through the Boot Loader Specification `devicetree` field and hands it
to the EFI-stub kernel. This approach has booted successfully on this device, so
there is no need to keep packaging the kernel, initrd, DTB and command line into a
UKI. The current path also does not need an extra `dtb=` parameter.

Early investigation found that the nabu Linux DTB resource in the Aloha sources used
here is placeholder content; that shows the firmware cannot be relied on to provide
a suitable device tree, but it does not mean the firmware can only boot a UKI.
Different firmware builds may differ, and this finding should not be generalised
into a fixed defect of all Aloha firmware.

The current external-DTB boot path assumes firmware with Secure Boot disabled; this
project does not provide Secure Boot signing or key management. Upstream systemd-boot
skips unverified external DTBs when Secure Boot is enabled. See the
[systemd-boot source](https://github.com/systemd/systemd/blob/main/src/boot/boot.c)
and the
[device tree loading implementation](https://github.com/systemd/systemd/blob/main/src/boot/devicetree.c).

## What each generation is bound to

When you run `nixos-rebuild boot` or `switch` on the device, the nixpkgs installer
reads each generation's bootspec, generates the matching boot entry and deploys the
required boot files. The `init=` in the entry points at a specific store closure,
not at a mutable entry point such as `/nix/var/nix/profiles/system/init`.

Different generations can reference the same kernel, initrd or DTB. When only
userspace changed and the boot files did not, there is no need to store a complete
boot image again on the ESP; when the kernel or initrd changes, old entries keep
using the old files. File retention and cleanup are managed by the nixpkgs
systemd-boot installer, but the free space on the ESP still needs attention.

Rollback covers the NixOS system configuration and package closures. It does not
include `/home`, databases or other mutable data, and it is not a rollback of the
whole UEFI firmware. The optional tmpfs root + Btrfs profile is described in the
[storage profile](storage.md) guide; it retains selected state and does not create
data snapshots automatically.

## Difference between the initial image and routine updates

`system.build.esp-image` in [`nixos/images/esp.nix`](../nixos/images/esp.nix)
assembles the initial FAT image in an ordinary build environment:

| Initial ESP path | Contents |
| --- | --- |
| `EFI/BOOT/BOOTAA64.EFI` | systemd-boot fallback entry |
| `EFI/systemd/systemd-bootaa64.efi` | systemd-boot vendor path |
| `EFI/systemd/drivers/GopRotate_aa64.efi` | menu rotation driver |
| `EFI/Android/Reboot2Android.efi` | Android boot program |
| `loader/entries/nixos-nabu.conf` | initial generation 1, bound to the matching closure |
| `nixos/kernel`, `nixos/initrd`, `nixos/nabu.dtb` | initial boot files |

This part is still the project's own image packaging logic and does not run the full
on-device installer inside the build sandbox. Routine rebuilds use the names and
paths generated by the nixpkgs installer, so they should not be assumed to stay
`nixos-nabu.conf` or `/nixos/kernel` forever. The initial image's files should not be
assumed to be cleaned up entirely by that installer either; handle them manually only
after confirming that no boot entry references them.

[`nixos/images/rootfs.nix`](../nixos/images/rootfs.nix) puts the same system closure
into the selected ext4 or Btrfs layout, creates the initial profile link and
registers the Nix store database on first boot. Both image entry points live under
`config.system.build`, and the flake only composes configuration and exports
artifacts. The ESP and the rootfs must come from the same configuration evaluation
and must not be mixed freely across two releases or across native/cross-built
artifacts.

## Code entry points

- [`nixos/boot.nix`](../nixos/boot.nix): boot loader, DTB, Android, rotation driver and boot logging.
- [`nixos/hardware-nabu.nix`](../nixos/hardware-nabu.nix): kernel, drivers, firmware, partitions and device services.
- [`nixos/configuration.nix`](../nixos/configuration.nix): base system configuration and module composition.
- [`nixos/niri.nix`](../nixos/niri.nix), [`nixos/niri.kdl`](../nixos/niri.kdl): the current desktop.
- [`flake.nix`](../flake.nix), [`scripts/build-image.sh`](../scripts/build-image.sh): build and export.
